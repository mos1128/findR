## M4 3a 的前置调研：RN 侧 crypto 结论（别再重复调研）

翻了一遍 **expo-crypto 57.0.3** 的实际代码（`node_modules/.pnpm/expo-crypto@57.0.3_...`）：

- **自带原生 AES-GCM**：`expo-crypto/build/aes` → `AESEncryptionKey.import(bytes)` /
  `aesEncryptAsync` / `aesDecryptAsync` / `AESSealedData.fromParts(iv, ct, tag)`。
  原生模块名 `ExpoCryptoAES`，Android 实现是 `javax.crypto` 的 `AES/GCM/NoPadding`
  （`android/src/main/java/expo/modules/crypto/aes/`）。
  ⇒ **不需要新增任何原生依赖**，它已经随现有 expo-crypto 编进 APK 了。
  （原先「crypto 没装实现库、要么 quick-crypto 要么 WebCrypto」的判断作废）
- ✅ **16B nonce 的疑虑解除**（原列为「必须实测」）：`EncryptOptions.gcmParameterSpec()`
  直接把调用方传入的 IV 放进 `GCMParameterSpec(tagBits, iv)`，**无长度校验**（默认 12 只是默认值）；
  解密侧从 sealed data 读回同一 IV。Conscrypt 支持非 12 字节 IV ⇒ 设计文档的 16B 布局可行。
- ⚠️ **缺口：没有 KDF**。expo-crypto 只有 digest / random / AES，无 PBKDF2。
  `digestStringAsync` 循环 60 万次 = 60 万次 bridge 调用，不可行。
  计划：`@noble/hashes` 的 pbkdf2（纯 JS、Hermes 可用）放
  `apps/mobile/src/platform/crypto.ts`；**必须分片 + await 让出主线程**，
  否则 600k 迭代会把界面冻住。实测太慢再换 `react-native-quick-crypto`（只动这一个文件）。
- 相关事实：`apps/mobile/src/capture/submit.ts` 已经在用 `expo-crypto` 的 `randomUUID`
  （所以自检屏那行「crypto.randomUUID 不可用（已走兜底）」不是 bug）。

## 场景/降级逻辑梳理（用户要求「覆盖各场景」后重读代码所得）

用户说「和我预想的不一致」，于是把**决定行为的开关**重新读实了一遍。真正的开关是三个：
**S1 配没配主模型**（`llmConfigured`：model 非空 且 openai-compat 需 baseUrl；**API Key 不参与判定**）、
**S2 端点可达吗**（"有网"只作用在这里）、**S3 配没配 ASR**。结论三档：
全配可达＝全功能；S1✅ 但 S2/S3 缺＝可用但打折；**S1❌＝只剩记事本**。

几条**最容易讲错、下次别再讲错**的：

- **「没配模型」比「配了但断网」更糟**：断网时搜索能走兜底字面查；没配模型时 `runSearch`
  第一步就抛，**连兜底都到不了**，UI 只剩「没找到相关记忆」（静默 + 误导）。
  首页提示条只覆盖 `offline || noAsr`，**从不提示"没配模型"**
- **兜底搜索不做中文分词**（`buildRawSearch` 只按标点/空格切）：整句无空格 ⇒ 整串成一个 FTS
  短语 ⇒ 几乎必然 0 条。**断网时"用句子搜"基本搜不到**。这是设计缺口，用户会当故障
- **没有后台定时重试**：队列触发点只有「录入保存后 / App 回前台 / 手动点一次」。
  首页文案「稍后联网会自动补上解析」在导出 BackgroundFetch 之前，**依赖用户切前台**才成立
- **`unclear` / `usedFallback` 两个信号 UI 完全没用**（core 已算好，只差展示）；
  断网搜到 0 条会触发 L2，失败后把 `error` 当答案显示
- **更正上一轮的错判**：早前记的「未配模型时 `requestAnswer` 抛未处理 Promise 拒绝」**不成立**
  （`runSearch` 先抛，走 `catch`，到不了 `res.cards.length===0`）。已在交接文档里标注更正

## 第六版：用户提的 4 个问题（2026-09-18 下午）

第 2 条是真 bug，第 1/4 条是同一个逻辑缺陷，第 3 条是需求修订。四条**用户都是对的**。

### ① 幽灵弹窗（真 bug，且上一版误诊）

用户：「点击进入卡片详情后提示位置树还是空的，这个界面现在 UI 正常，但返回依旧无法用，
右上角的关闭点击也无效，只能重启软件。」

**真根因**：`card/[id].tsx` 的 `LocationPickerModal` 内部写的是

```tsx
<Modal visible animationType="slide" onRequestClose={onClose}>
```

JSX 布尔简写 **`visible` ≡ `visible={true}`**（不是「沿用同名 prop」）。而该组件
**被无条件渲染**（`<LocationPickerModal visible={pickerOpen}>`），组件内又**没有**
`if (!visible) return null` 守卫 —— `CameraModal` 恰好有这道守卫，所以相机一直正常、
位置弹窗一直坏。⇒ 一个全屏 Modal 从**进入详情页那一刻**起就恒显示：视觉完全正常，
但所有触摸都被它接住；「关闭」的 `onClose` 其实执行了，可 `setPickerOpen(false)` 时
`pickerOpen` 本来就是 `false`，状态没变化 ⇒ 看起来「点了没反应」。

**上一版（apk-m1-fix1）为什么没修好**：误诊为「边到边 + 状态栏吃掉顶部触摸」，只补了
`paddingTop: insets.top` —— 那解释了「顶到状态栏」，解释不了「整屏点不动」。
用户复验说「UI 正常了但仍点不动」，正好印证。

**修法**：两处 Modal 都改 `visible={visible}`；补 `if (!visible) return null`（CameraModal 同步改）；
`paddingTop` 保留（它是另一个真实问题）。

**教训（已写进交接文档）**：真机报「界面看着正常但点不动 / 关不掉」⇒
**先怀疑上面盖了一层透明的全屏东西吃掉了触摸**，而不是先怀疑安全区。
判别法：**能看见的元素 ≠ 能点到的元素 ⇒ 上面盖了东西。**

### ② 检索不该依赖模型（问题 1 + 4：用户认为两者应是同一逻辑）

用户问：「配了模型·端点不通」和「没配模型」不应该是同一个逻辑吗？并进一步说：
有人出于隐私考虑就是不想把内容传给模型，一直离线也得能用基础能力。

**用户是对的**。原实现：未配模型 ⇒ `runSearch` 在 `buildAdvanceDeps` 就抛 ⇒ 连字面检索都到不了；
配了但断网 ⇒ `searchCards` 内部 catch 掉、走 `buildRawSearch` 兜底 ⇒ 可用。
同一件事两条路，且**更常见的那条（压根不想配模型）反而更不可用**。

**修法**：`searchCards` 的 `llm`/`cfg` 改可选，缺失时跳过 P2 直接字面兜底；
`runSearch` 不再抛错；`runAnswer` 无模型返回 `{ok:false}` 而非抛错；
`index.tsx` 加 `searchNote` 说明本次走哪条路（顺带把 core 早算好却没人用的
`unclear`/`usedFallback` 接上 UI）；无模型时不触发 L2、不显示「AI 总结」按钮；
首页提示条补「还没配置模型」口径 —— 对不配模型的用户不再承诺「稍后联网会自动补上解析」（假承诺）。

### ③ 离线中文整句搜不到（问题 4 的另一半）

`buildRawSearch` 只按标点切分：`我的护照在哪` 整串被当成一个 8 字 FTS 短语，
与卡片原文的连续子串对不上 ⇒ 必然 0 条。「离线也能搜」实际变成「离线搜不到」。

**修法**：标点切分后再按虚词/疑问词切一遍（我的/在哪/什么/没有/了/吗…），落到实词上；
**刻意不收单字的「在/放/找」** —— 那会切坏「现在」「放心」「寻找」。

### ④ 位置树应由解析增量维护（问题 3）

用户：「位置树这个东西不应该让用户自己配，而是增量维护才对。比如用户说『放在次卧的左侧床头柜了』，
模型解析完发现之前已经有这个位置了就复用，没有就新建。用户可选自己去修改/新建，
但是不应该让用户必须自己加。」

**需求原文（需求.md 第 122 行）本就写着**「优先从已有位置树中匹配，匹配不到才让用户点选或新建」，
而实现把「让用户新建」做成了「必须用户自己建」，主次颠倒 —— 位置树为空时连点选都没得选。

**修法**：新增 `ensurePath`（逐级查找：先查 `aliases.kind='location'` 再按同名；缺失则
`upsertLocation` 新建，返回 `created`）；解析落位改用它；`path_matched` 改由
「本次是否新建过节点」决定（比模型自报可靠）；新建 ⇒ `needsConfirm=1`，卡片上标「新位置」；
`resolvePath` 保留为只读版本（导入合并等场景用）。需求.md 第 122 行同步修订并注明修订原因。
