# 2026-09-20

## 分析：把「AI 总结」并进搜索框的成本 / 速度影响

用户问「搜索调一次模型、AI 总结再调一次，若合并到搜索框体验影响多大（费用、速度）」。
做了基于真实 prompt 模板的量化测算（不是估的，是从 `templates.ts` 提取模板重建请求后按字符统计）。

### 两条链路的实测规模（单次搜索）

| | 输入 | 输出 | 合计 |
|---|---|---|---|
| L1 检索（`searchCards` / P2） | ≈570 tok | ≈55 tok | **≈625 tok** |
| L2 答案组织（`answerFromCards` / P3） | ≈971 tok | ≈51 tok | **≈1022 tok** |
| 合并后每次搜索 | ≈1541 tok | ≈106 tok | **≈1647 tok** |

- **纠正一个直觉误区**：说「搜索只传少量内容」只对一半。L1 的 **user 部分**确实只有问句（6 字），
  但 system 有 1486 字 ≈566 tok（分类 + 位置树 30 条 + schema + 规则 + 2 条 fewshot），每次都发。
  L2 反过来：system 只有 248 字，但 user 的 8 条命中片段有 1665 字 ≈856 tok。
- 换算：每次搜索 token 约 **2.6 倍**，模型调用次数 **1 → 2**。

### 费用（按 DeepSeek-V4-Flash 空闲时段价，2026-08-17 调价后）

价目：输入（缓存未命中）1.5 元/百万、命中 0.05 元/百万、输出 4.5 元/百万。

- 每 1000 次搜索：只搜索 ≈1.10 元，合并后 ≈2.79 元（缓存未命中）；有 prompt cache 时 ≈0.28 → 1.80 元。
- **结论：费用完全不构成理由。** 折算每次多花约 0.0015 元（0.15 分）；按一天 20 次搜索算，
  一年差额约 10 元量级。→ `需求.md` 5.3 里写的「每次跑会白花一次模型调用」其实是所有理由里**最弱的一条**。

### 速度（这才是真代价）

- 需求既定指标：L1 P95 ≤ 3s、L2 P95 ≤ 5s；**串行最坏 8s**。
- 若只做「阻塞式合并」（等两次都回来再渲染）——列表被答案拖住，体感明显变慢。
- 但可以做「**渐进式合并**」：先渲染列表，答案随后补上。这样延迟几乎被阅读列表的时间吸收，
  等于现在的「手动点」变成「自动补」，速度上几乎免费。

### 比费用/速度更该权衡的两条（本轮新识别）

1. **隐私**：L2 每次外发最多 8 条记忆片段（`L2_MAX_SNIPPETS=8`）。现状是用户不点按钮就**不外发**；
   合并后 = **每次搜索都外发记忆内容**。对「个人记忆库 + 隐私优先」的产品定位，这是最实质的变化。
2. **错误归因**：L2 可能挑错卡。现在挑错是「用户主动要的结果」，合并后变成「系统自动给的结论」，
   会削弱信任。另外有结果时总结往往只是**复述**可扫的列表，信息冗余。
3. 附带发现：`providers/types.ts` 的 `usage`（inputTokens/outputTokens）虽被解析，但**全项目没有任何地方落库或显示**
   → 想要真实的 token 账单，先得把它接出来（目前只能靠估算）。

### 建议口径（未落地，待用户拍板）

不要合并成「一次调用」，但可以考虑合并成「一次交互」：搜索出列表 + 底部自动追加答案（渐进式）。
若要做，建议加开关「每次搜索都自动组织答案」**默认关**，把成本与隐私的选择权留给用户。

### 顺带诊断：L1 的三种「静默空」（已复现，未修）

用户报「搜『国外出行需要准备哪些证件』为空，但该能搜到护照卡」。用真实 DB + 假 LLM 逐条复现，
已固化为测试。**卡与索引都没问题，空结果必来自 P2 的决策**：

| P2 决策 | 命中 | UI 提示 |
|---|---|---|
| 关键词含「证件」+ `any` / 只给「证件」+ 分类对 / 同义词扩出「护照」 | **1 ✓** | — |
| ① `match_mode=all`（AND 过严） | 0 | ❌ 静默 |
| ② 意图判成「待买补货」⇒ 分类过滤剔掉物品卡 | 0 | ❌ 静默 |
| ③ 关键词里没有「证件」 | 0 | ❌ 静默 |
| ④ `intent=unknown` ⇒ `buildSearch` 返 null，一次查询都不发 | 0 | ✅ unclear 有提示 |

- 关键事实：**「证件」是 2 字词**，trigram 产不出 token，靠 `splitTerms` 降级 LIKE；
  LIKE 带 `c.tags` ⇒ 只要这个词进了关键词就一定命中。**失败不在检索层。**
- 待拍板的修法：① L1 空结果时**逐级放宽约束重试**（先去掉分类过滤，再把 `all` 降为 `any`）；
  ② `intent=unknown` 时**退回字面兜底**（与「未配模型」走同一条路 —— 现在的行为自相矛盾：
  未配模型有兜底，配了模型但模型说听不懂反而直接空）。

## 检索需要重新设计 —— 用户 2026-09-20 的产品级质疑（**未动代码，等拍板**）

用户原话：「命中逻辑还是在无脑搜索……我们做的是长程记忆，要把 AI 当真实助手来用，而不是无脑匹配。」
期望样例：库里有 护照 / 螺丝刀 / 插线板 / 剃须刀，问「我去国外玩应该会用到哪些东西」
→ 应返回 **护照、剃须刀**（而不是靠字面命中）。

### 诊断：三处独立的锁死（读的是 prompt 原文，不是推测）
1. `P2_SYSTEM` 规则 2「**绝不假设库里存在什么物品**」+ 规则 3「关键词必须来自问句本身」
   ⇒ 「国外玩带什么」只能产出「国外 / 玩 / 东西」，**永远产不出「护照」「剃须刀」**
2. 本地 FTS / LIKE 是字面匹配 ⇒「旅游」与「护照」零字面重叠，必然匹配不上
3. `P3_SYSTEM` 规则 1「**不得补充片段之外的任何信息**」⇒ 即便有片段，也不许用世界知识推理

**结论：不是实现粗糙，是规格只允许它做字面检索。** 定位题（我护照放哪了）本该如此；
推理题（出国带什么）**本质需要把「库存」喂给模型** —— 而模型从始至终没见过库存。

### 已提出的新架构（待用户拍板）
- P2 增加 `mode` 路由：`locate`（词法，现状保留）/ `advise`（推理，新）
- 推理通道 = **宽召回（本地：情景联想词 + 分类白名单，只求不漏）
  → 库存轻索引（实体名 + 分类 + 位置，**不含 desc / 原文**）
  → 模型裁决（用世界知识判相关度）→ 只列相关项 + 说明缺什么**
- 核心反转：现在是「窄召回 + 零裁决」（既漏又杂），改成「**宽召回 + 严裁决**」
- 建议裁决三档（必需 / 看情况 / 不相关）——「插线板」这类边界项能诚实表达成
  「看情况，取决于插座标准」；二分类会误删对的或全留成噪音
- 新增 `missing` 输出：「你没记过转换插头」是助手的义务，现有 P3 被禁止做到
- 隐私边界必动：定位题仍只发问句；推理题需发**结构化物品清单**（不含描述与原文）。
  这条是产品承诺，**必须用户拍板**
- 流程题（换驾照怎么办）**不走新通道** —— 它与卡片共享实体名，词法本来就能命中，不是同类病
