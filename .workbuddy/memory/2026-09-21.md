### 问题 1：录入入口是否收成一个（像 AI 聊天助手）
用户的提案：只留一个入口 → 选语音或打字；`+` 展开可加图片 / 文件。

我给的结论（分两半，理由都落到代码/文档上）：
- **同意**：录入侧确实该收成一个底部输入条。查代码发现现状是三个入口两条路 ——
  `📷→/capture?mode=photo` 与 `⌨️→/capture?mode=text` **通到同一个 CaptureScreen**（三个面板全在），
  只有初始 `cameraOpen` 不同；而底部 `🎙️ 长按` 是完全不同的行为（`persistCapture` 直接落盘、
  不进任何页面）。且 `mode=text` 没给输入框 `autoFocus`（`capture.tsx` 未传）⇒ 打字比语音多两步。
- **反对**：把「记」和「查」合成一个输入框由模型自动分路。判错代价不对称：
  查→记 只是多一条垃圾卡（可见可恢复）；**记→查 是用户以为存下了其实没存**（不可发现），
  与「先落盘、素材永不丢失」的产品红线直接冲突。建议做成同一组件的两种模式 + 左端图标切换。
- **反对**：把整屏改成聊天记录流。场景分析原则 2 说检索是「短、急、确定性高」；
  且本产品第三个动词是「翻」（记忆流 + 分类 chips 是唯一的浏览面），聊天流做不了翻。

### 问题 2：查物是否改成「两次连接大模型」
用户的提案：第一次 AI 分析这句话涉及哪些东西 → 本地检索 → 第二次把结果交给 AI 二次过滤，理由是省 token。

我给的结论：
- **第一步已经存在** —— 那就是 `P2`（keywords / synonyms / category / path_prefix / time_hint / match_mode）。
  所以真正的提案是「给定位题**加**一次调用」。
- **不会省 token，反而固定多花一次**。定位题的外发量**与库大小完全无关**：
  P2 只发问句（6 字），L2 只发命中片段（`L2_MAX_SNIPPETS = 8`，desc 240 / transcript 160 硬截断）。
  加上那次过滤调用 = 1,647 token/次（今天的 autoAnswer 开启路径就是这个量），约 2.6 倍。
- **会随库增长的只有推理题**（P4 发整库清单，已封顶 `INVENTORY_LIMIT = 200` ≈ 1.6 万 token ≈ 2 分钱/次）。
  但那里的瓶颈**不是钱，是注意力**（清单越长模型越看漏，这条交接文档本来就有）。
- **真正该修的缺陷**（顺着用户的直觉找到的，可验证）：
  `buildInventory` 走 `listCards` = `ORDER BY created_at DESC` ⇒ 清单是「**最近**的 200 条」。
  而「最近」和「这次出行用不用得上」零相关 —— 库一大，清单被无关新卡占满，
  **护照是去年记的，正好被截在 200 之外**。这是随库增长而恶化的真实缺陷，
  且修它**不需要任何额外模型调用**（本地按 aspects / scenario 的词面重合度排序后再截断）。
- 顺手可省：清单里 uuid 列 ≈10 token/行（约占 11% 体积），而模型只需「序号」就能回指，
  本地按序号映射回 id 即可（再用 id 做防幻觉校验）。200 行省 ≈2,000 token。
- 若将来真到 >200 条且嫌不准：两级裁决（先发「分类+实体名」目录圈范围，再发完整清单）
  —— **那才是用户这套「两次调用」的正确适用位置**（推理题 + 超大库），不是定位题。
- 折中方案（若只是想提精度）：让模型**重排、不删除**（ranker 而非 filter），
  其余结果留一行分隔线继续显示 —— 永不引入「静默删掉正确答案」这个失败模式。

## 用户追问：「Hermes 字符串表是什么？」→ 把字节码格式真正解析清楚了

上一轮那个「包内探针」手法当时只是**试出来的**（试了 utf-8 不中、换 utf-16-le 就中），
没弄清为什么。这一轮从 Hermes 源码把它查实，并把手法固化成脚本。

### 查实的格式（本包 `apk-m1-fix11` 的 `assets/index.android.bundle`，Hermes v98）
- 8 字节 magic `0x1F1903C103BC1FC6`（源码注释：**"Hermes" 的古希腊文写法的 UTF-16BE 截断成 8 字节**）
  + 4 字节版本号（98）。`fileLength` 在头偏移 32 —— 用它自检解析对不对。
- 段顺序由 Hermes 源码 `visitBytecodeSegmentsInOrder` 定死：
  `header → 函数头 → stringKind → 标识符哈希 → 字符串表 → 溢出表 → 存储区 → …`
  （**函数头在字符串表之前**，这点凭直觉猜会猜反。）
- 本包实测区间（误差 0 字节，三处算术互相咬合）：
  header `[0,128)` / 函数头 `[128,159464)`（13278 × **12 B**）/ stringKind `[159464,159476)`（3×4）/
  标识符哈希 `[159476,204816)`（11335×4）/ **字符串表 `[204816,273724)`（17227×4）** /
  溢出表 `[273724,274292)`（71×8）/ 存储区 `[274292,565448)`（291156 B）。
- 每个表条目 **4 字节**：`isUTF16:1 + offset:23 + length:8`（位域，LSB 起）。
  长度 255 或偏移 ≥2²³ ⇒ 溢出，转去 8 字节的溢出表。
- 字符串表里 **单字节 16564 + 双字节 663**（含汉字 599 条）。**只要有一个非 ASCII 字符
  （含 emoji），Hermes 就整串按 UTF-16 存** ⇒ Android/PC 都是小端 ⇒ 文件里就是 UTF-16LE。
  这就是「grep 找 UTF-8 中文永远 0 命中」的根因。
- 存储区还有**后缀共享**：3624 条的存储借用了别的串的一段（起点重合），
  所以各条长度相加 363966 > 存储区 291156；无一越界。

### 两条硬规矩（第 1 条是这次真正学到的）
1. **模板字符串按 `${}` 切断存，插值处必然断开**，编译器还会把相邻字面量合并。
   源码 `` `（全库共 ${total} 条，此处只列出${x ? '与本次问题最相关的' : '最近的'} ${n} 条` ``
   在包里只剩 ` 条，此处只列出`(条目 #5597)、`与本次问题最相关的`(#5784)、`最近的`(#6014)。
   ⇒ **片段比整句命得准**；探针要选源码里字面写出的一段，且别跨 `${}`。
2. 字符串**去重**（全文只 1 次）⇒「0 次」一定能证明没进包；「1 次」不代表只在一处用。

## 用户提出：认证方式「bear 和 x-api-key 两种，是不是不需要两种」→ 已查实，等拍板

**用户是对的，而且比他自己说的更彻底。**（查证来源：Anthropic 官方文档 2026-09 现状，
docs.anthropic.com / docs.claude.com / platform.claude.com 三处一致）

- 官方现在的头表：`Authorization: Bearer <你的 API key 或短期 token>` 标注为
  **「必填，除非设了 x-api-key」**；`x-api-key` 的说明是
  **「Legacy fallback for Authorization, still supported（旧版兜底，仍受支持）」**。
  ⇒ **Bearer 已是官方首选，x-api-key 退化成兼容项。**（Anthropic 早期只认 x-api-key，
  我们实现时按当时事实写了 `// Anthropic 原生 x-api-key；本地网关 bearer` —— 那句注释现在过期了。）
- 🔴 **我们 UI 的标签是反的**：`settings/provider.tsx:234,239` 写「**x-api-key（官方）**」/
  「Bearer（网关）」。现在官方首选是 Bearer —— 这个「官方」二字会主动把用户往旧路上推。
  （官方仍接受 x-api-key，所以在官方 API 上点错不会坏；但配网关时点错就直接 401，
  而且用户会误以为 key 填错了。）
- **这个选项只影响 Anthropic 协议**：`openai-compat.ts:31` 里 `authorization: Bearer` 是写死的，
  选「OpenAI 兼容」时这一行根本不出现 ⇒ 它其实是「Anthropic 协议的认证头怎么发」。
- `需求.md` grep `authStyle|x-api-key|Bearer|认证` **零命中** ⇒ 它从没进过需求，是实现层的自选项，
  删掉不算改范围。
- 现有安装里存的 `authStyle:'bearer'` 被忽略也无害（默认就是 bearer），**覆盖安装无需迁移**。

### 我的建议（待用户拍板，**尚未改任何代码**）
删掉 UI 那一行选项；适配器**默认只发 Bearer**，**仅在 401/403 时自动换 x-api-key 再试一次**。
- 为什么不彻底删掉 x-api-key：那会让「只认 x-api-key 的老端点」彻底无解（这个 App 改一次要一轮 CI）。
  兜底只多 4 行，把这一类失败永久消掉；Anthropic 适配器本来就在处理网关差异
  （伪装 UA、SSE/非 SSE 双形态、`anthropic-version`），加认证头兜底与它的性格一致。
- 为什么不是「两个头一起发」：查不到官方对「同时带两个」的明确说法 —— **猜的东西不进代码**。
- 为什么只在 401/403 兜底：这两码是「HTTP 层说凭证不被接受」，与**铁律 5**（「调用失败」与
  「能力不支持」必须分开判）同源；其他错误不重试，避免掩盖真实失败。
- 方案若采纳，改动面：`providers/types.ts:69-70`、`providers/anthropic.ts:53-54`、
  `settings.ts:39`、`settings/provider.tsx:93-95,119,155,231-243`、
  `test/providers.test.ts:160-185`；文档 `技术设计.md:212`、`开发交接.md:1495,1580`、`测试计划.md:52`。
- 可与「设置页两处过期文案」（本文件上一节）**合并成 fix12 一起出**，省一轮装机。
