### 问题 1：录入入口是否收成一个（像 AI 聊天助手）
用户的提案：只留一个入口 → 选语音或打字；`+` 展开可加图片 / 文件。

我给的结论（分两半，理由都落到代码/文档上）：
- **同意**：录入侧确实该收成一个底部输入条。查代码发现现状是三个入口两条路 ——
  `📷→/capture?mode=photo` 与 `⌨️→/capture?mode=text` **通到同一个 CaptureScreen**（三个面板全在），
  只有初始 `cameraOpen` 不同；而底部 `🎙️ 长按` 是完全不同的行为（`persistCapture` 直接落盘、
  不进任何页面）。且 `mode=text` 没给输入框 `autoFocus`（`capture.tsx` 未传）⇒ 打字比语音多两步。
- **反对**：把「记」和「查」合成一个输入框由模型自动分路。判错代价不对称：
  查→记 只是多一条垃圾卡（可见可恢复）；**记→查 是用户以为存下了其实没存**（不可发现），
  与「先落盘、素材永不丢失」的产品红线直接冲突。建议做成同一组件的两种模式 + 左端图标切换。
- **反对**：把整屏改成聊天记录流。场景分析原则 2 说检索是「短、急、确定性高」；
  且本产品第三个动词是「翻」（记忆流 + 分类 chips 是唯一的浏览面），聊天流做不了翻。

### 问题 2：查物是否改成「两次连接大模型」
用户的提案：第一次 AI 分析这句话涉及哪些东西 → 本地检索 → 第二次把结果交给 AI 二次过滤，理由是省 token。

我给的结论：
- **第一步已经存在** —— 那就是 `P2`（keywords / synonyms / category / path_prefix / time_hint / match_mode）。
  所以真正的提案是「给定位题**加**一次调用」。
- **不会省 token，反而固定多花一次**。定位题的外发量**与库大小完全无关**：
  P2 只发问句（6 字），L2 只发命中片段（`L2_MAX_SNIPPETS = 8`，desc 240 / transcript 160 硬截断）。
  加上那次过滤调用 = 1,647 token/次（今天的 autoAnswer 开启路径就是这个量），约 2.6 倍。
- **会随库增长的只有推理题**（P4 发整库清单，已封顶 `INVENTORY_LIMIT = 200` ≈ 1.6 万 token ≈ 2 分钱/次）。
  但那里的瓶颈**不是钱，是注意力**（清单越长模型越看漏，这条交接文档本来就有）。
- **真正该修的缺陷**（顺着用户的直觉找到的，可验证）：
  `buildInventory` 走 `listCards` = `ORDER BY created_at DESC` ⇒ 清单是「**最近**的 200 条」。
  而「最近」和「这次出行用不用得上」零相关 —— 库一大，清单被无关新卡占满，
  **护照是去年记的，正好被截在 200 之外**。这是随库增长而恶化的真实缺陷，
  且修它**不需要任何额外模型调用**（本地按 aspects / scenario 的词面重合度排序后再截断）。
- 顺手可省：清单里 uuid 列 ≈10 token/行（约占 11% 体积），而模型只需「序号」就能回指，
  本地按序号映射回 id 即可（再用 id 做防幻觉校验）。200 行省 ≈2,000 token。
- 若将来真到 >200 条且嫌不准：两级裁决（先发「分类+实体名」目录圈范围，再发完整清单）
  —— **那才是用户这套「两次调用」的正确适用位置**（推理题 + 超大库），不是定位题。
- 折中方案（若只是想提精度）：让模型**重排、不删除**（ranker 而非 filter），
  其余结果留一行分隔线继续显示 —— 永不引入「静默删掉正确答案」这个失败模式。

## 用户追问：「Hermes 字符串表是什么？」→ 把字节码格式真正解析清楚了

上一轮那个「包内探针」手法当时只是**试出来的**（试了 utf-8 不中、换 utf-16-le 就中），
没弄清为什么。这一轮从 Hermes 源码把它查实，并把手法固化成脚本。

### 查实的格式（本包 `apk-m1-fix11` 的 `assets/index.android.bundle`，Hermes v98）
- 8 字节 magic `0x1F1903C103BC1FC6`（源码注释：**"Hermes" 的古希腊文写法的 UTF-16BE 截断成 8 字节**）
  + 4 字节版本号（98）。`fileLength` 在头偏移 32 —— 用它自检解析对不对。
- 段顺序由 Hermes 源码 `visitBytecodeSegmentsInOrder` 定死：
  `header → 函数头 → stringKind → 标识符哈希 → 字符串表 → 溢出表 → 存储区 → …`
  （**函数头在字符串表之前**，这点凭直觉猜会猜反。）
- 本包实测区间（误差 0 字节，三处算术互相咬合）：
  header `[0,128)` / 函数头 `[128,159464)`（13278 × **12 B**）/ stringKind `[159464,159476)`（3×4）/
  标识符哈希 `[159476,204816)`（11335×4）/ **字符串表 `[204816,273724)`（17227×4）** /
  溢出表 `[273724,274292)`（71×8）/ 存储区 `[274292,565448)`（291156 B）。
- 每个表条目 **4 字节**：`isUTF16:1 + offset:23 + length:8`（位域，LSB 起）。
  长度 255 或偏移 ≥2²³ ⇒ 溢出，转去 8 字节的溢出表。
- 字符串表里 **单字节 16564 + 双字节 663**（含汉字 599 条）。**只要有一个非 ASCII 字符
  （含 emoji），Hermes 就整串按 UTF-16 存** ⇒ Android/PC 都是小端 ⇒ 文件里就是 UTF-16LE。
  这就是「grep 找 UTF-8 中文永远 0 命中」的根因。
- 存储区还有**后缀共享**：3624 条的存储借用了别的串的一段（起点重合），
  所以各条长度相加 363966 > 存储区 291156；无一越界。

### 两条硬规矩（第 1 条是这次真正学到的）
1. **模板字符串按 `${}` 切断存，插值处必然断开**，编译器还会把相邻字面量合并。
   源码 `` `（全库共 ${total} 条，此处只列出${x ? '与本次问题最相关的' : '最近的'} ${n} 条` ``
   在包里只剩 ` 条，此处只列出`(条目 #5597)、`与本次问题最相关的`(#5784)、`最近的`(#6014)。
   ⇒ **片段比整句命得准**；探针要选源码里字面写出的一段，且别跨 `${}`。
2. 字符串**去重**（全文只 1 次）⇒「0 次」一定能证明没进包；「1 次」不代表只在一处用。

## 浏览器预览的「账单」查证结果（2026-09-21 下午，别重新调研）

用户追问「能不能电脑上跑 SQLite 然后浏览器预览」。逐个查实（本地扒源码 + 官方文档）：

- **SQLite 这一环是最容易的，但必须选对包**：
  - ❌ `sql.js`（最有名的 WASM SQLite）**官方构建不含 FTS5**（社区多次确认；要自己 emscripten 重编
    `-DSQLITE_ENABLE_FTS5`）。我们的 L1 检索 ≥3 字走 `MATCH` ⇒ 用它直接废掉搜索。
  - ✅ `@sqlite.org/sqlite-wasm`（SQLite 官方维护）**含 FTS5**（900KB gzip），且 **oo1 API 是同步的**，
    正好卡上 core 那个同步 `SqliteDriver`。**主线程直接用就是纯内存库** ⇒ 不需要 Worker、
    不需要 COOP/COEP 响应头（OPFS 持久化才需要）。落库字节丢 IndexedDB 即可跨刷新保留。
  - ⚠️ npm 上裸名 `sqlite-wasm` 是 2020 年废弃的 0.0.2，**与官方无关，别装错**。
- **`react-native-web` 的 `Alert` 是空函数**（已扒 `dist/exports/Alert/index.js` 原文：
  `class Alert { static alert() {} }`）。**不报错、静默什么都不做** ⇒ 浏览器里点「删除」没有确认框，
  但删除照常执行。**这是预览里最危险的一处**，不是"打桩就行"，是必须换成自己的弹窗组件。
  用量：`Alert.` **28 处 / 7 个文件**。
- **Expo 各模块的 Web 支持（查的是官方文档平台徽标）**：
  | 模块 | Web | 结论 |
  |---|---|---|
  | expo-camera | ✅ | 直接用 |
  | expo-image-picker | ✅ | 直接用 |
  | expo-image-manipulator | ✅（含 WebP） | 直接用 |
  | expo-audio | ✅ | 直接用 |
  | expo-secure-store | ❌ 徽标只有 Android/iOS/tvOS | 桩 → localStorage |
  | expo-sharing | ❌ 文档原文「Web ❌，浏览器上不可用」 | 桩 → Blob 下载 |
  | expo-file-system（新 File/Directory API） | ⚠️ 官方博客自认 Web 不支持任意路径访问、「还在探索」 | 桩 → 内存/IndexedDB |
  | op-sqlite | ❌ 无 web 实现 | 见上（换 sqlite-wasm） |
- **技术栈一句话**：pnpm monorepo；`packages/core` 纯 TS（唯一运行时依赖 zod，测试用
  better-sqlite3 + vitest）；`apps/mobile` = Expo SDK 57 / RN 0.86.3 / React 19.2.3 / expo-router /

## 调研：要不要换栈（Flutter / KMP）—— 结论是**不换**，四条理由都硬
用户拿 `D:\my-document\浏览器下载\guoapp`（短剧 App）来问「是不是有更主流、支持双端、编译成本更低的方案」。

- **guoapp 是什么**：**Flutter（Dart UI，28 文件 9314 行）+ Go 原生核心**（`native/core` 走
  `go build -buildmode=c-shared`，Android 用 NDK clang、iOS 用 xcrun clang 出 XCFramework，

- **「体积小」是错觉**：guoapp 仓库 1.5M 是**纯源码**（`.gitignore` 掉 build/dist/node_modules 类）。
  我们 findR 文件夹在资源管理器里显得 1GB+，是因为 **node_modules 980M + `.workbuddy` 236M**；
  刨掉这两样，**我们自己的源码只有 2.9M**（core 5459 行 / 界面 4704 行 / 测试 3772 行）。
  两者同一量级，**不是方案差异**。
- **guoapp 的 iOS 其实没做成**（它自己 README 写死）：`iOS 15.1+ | 已加入工程、Go 核心链接、
  媒体依赖、文件管理和构建脚本；**待 Xcode 构建与真机验收，没有已签名 IPA**`；收尾记录还有
  「本机缺少 iPhoneOS SDK，iOS 尚未完成 Xcode 构建…本轮不运行远程 Actions」。**AGENTS.md 里
  iOS 排第 3 优先级（最后）**。⇒ 它**不能**作为「Flutter 让 iOS 变容易」的证据。
- **编译成本不存在栈级优势**：出包绕不开原生工具链（Gradle / Xcode / NDK）。
  guoapp 自己的 android job `timeout-minutes: 45`，**比我们 20~25 分钟更宽**；
  它还要 AOT 编译 Dart、塞 5 个 .so（libflutter/libapp/libmpv/libffmpegkit/libduanju_core）。
- **主流就三个，都"公认好用"**：Flutter / React Native(=Expo，我们) / KMP+CMP。
  CMP 的 **iOS target 自 1.8.0（2025-05）转正**，Flutter 一直稳，RN 一直稳 ⇒ **都支持双端**。
  选型真正取决于**团队已有语言**，不是能力差异。
- **iOS 那台 Mac 才是唯一的门**，三条绕法：① **EAS Build（我们栈自带，零改代码）**——Expo 官方
  云 macOS，免费额度 **15 次 iOS + 15 次 Android/月**，自动签名，`eas submit` 直传；

- **迁移代价（决定性）**：core 5459 行 TS + 测试 3772 行 + 界面 4704 行**全部重写**成 Dart/Kotlin；
  9 个平台端口逐个重找替代。（好消息：`sqlite3_flutter_libs` **默认带 FTS5**，
  我们用的 `tokenize='trigram'` 属于 FTS5 内置分词器，能平移。）

  但上一轮的 **dev client** 已经是同一量级 ⇒ 换栈买不到任何东西。

## 调研：全平台（Win / macOS / Linux + 手机）—— 结论仍是**不换栈，走"core + 多壳"**
- **真能六端一套代码的成熟方案只有两个**：**Flutter**（桌面 Win/macOS/Linux 官方一等公民、stable）
  与 **KMP + Compose Multiplatform**（桌面 Stable、iOS 自 1.8.0 转正）。
- **排除项**：.NET MAUI **Linux 官方不支持**；RN 桌面靠微软维护的社区端口、**Linux 基本没有、不是单二进制故事**；
  Tauri 2 六端能出但**桌面三端各用系统 WebView（WebView2 / WKWebView / WebKitGTK）渲染不一致**（Linux 老发行版尤其糟）+ 后端 Rust；
  Electron 只有桌面无移动端；Qt 能力最强但代价最大。
- **关键发现：我们不需要"一个栈管六端"**。core 5459 行 + 3772 行测试**零原生依赖**，
  **已经在两个运行时上跑通过**（手机 op-sqlite / 电脑 better-sqlite3）⇒ **桌面就是 better-sqlite3 的主场**，
  跑 `pnpm check` 时 core 的检索、排序、FTS5、备份打包**已在 Windows 上真实跑过**。
- **路线 B（推荐）**：手机端一行不动；桌面加 **Electron** 壳 ⇒ ①主进程是 Node.js，**core 零改动**，
  better-sqlite3 直接用；②渲染层是 Chromium ⇒ **上一轮评估的 react-native-web 平台层从"开发便利"
  升级成三端产线代码**，`ui/kit.tsx`（277 行自建组件）可整块复用；③三端同一 Chromium，渲染一致。
  代价：better-sqlite3 是原生模块要 `@electron/rebuild` 重编 + `asarUnpack`（**expo.useLegacyPackaging 那套经验不通用**）；
  macOS 分发要签名 + 公证（CI 侧，**仍不需要自购 Mac**）；安装包带 Chromium，100MB 级。
- **Apple 这道门两条路都躲不开**：iOS 与 **macOS**（桌面）构建都要 macOS 机器，macOS 分发还要 Gatekeeper 签名公证。
- **待用户拍板的产品问题**（决定"界面层"那格成本量级）：桌面版是「手机界面拉大」还是「专门一版桌面 UI」
  （侧栏 / 快捷键 / 拖拽入图 / 多窗口）？前者小工作量，后者等于第二套设计。
- **建议节奏**：① 先把手机双端做完整（iOS 只差一个 EAS 配置 + $99）；② 桌面按需再来，
  **甚至可以先做成"纯读版"**（导入 findrpack → 检索 → 导出），成本极低因为 core 零改动；
  ③ Linux 最后（个人 App 的 Linux 桌面用户极少，先 Win + macOS）。**别一次上六端。**

### 技术栈选型（用户问「不考虑重写成本，最佳是什么」，含界面通用性与体积）

**🔴 最重要的发现：`sqlite3_flutter_libs` 已废弃。**

`flutter pub add sqlite3_flutter_libs` 装出来的是 **`0.6.0+eol`**，README 原文：
> [!CAUTION] This package relates to version 2.x of `package:sqlite3`, and is obsolete after upgrading.
> Starting from version `0.6.0`, **this package no longer does anything.**

机制变了：**`package:sqlite3` 3.x 改用 Dart [build hooks](https://dart.dev/tools/hooks)**
自己把预编译 SQLite 打包进应用（所以 `dart pub add sqlite3` 会带进
`native_toolchain_c` / `hooks` / `record_use`）。官方升级说明明确写着「升级后请把
`sqlite3_flutter_libs` 删掉」。⇒ **已从 app 的 pubspec 里移除**。

**决定性证据（`sqlite3-3.6.0/doc/hook.md`）**：默认预编译二进制的编译选项里**含 `SQLITE_ENABLE_FTS5`**
（还有 DBSTAT_VTAB / RTREE / MATH_FUNCTIONS 等），且 **Android / iOS / macOS / Linux / Windows /
Web 全覆盖**，Android 具体到 `armv7a / aarch64 / x86 / x64`。
上游原话就是：系统自带的库「编译选项不一致、版本常常太旧」，所以它自带一份
⇒ **各平台能力一致**，正好对上我们最怕的那件事。

**⇒ 交接文档里「`sqlite3_flutter_libs` 默认带 FTS5 / app 必装它」这条口径全面作废，已改写**
（§2 硬证据、§4.1 设计点、§4.5、§6.0、§6.1 都改了）。
