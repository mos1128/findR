## 第十一版：修用户真机报的三条界面问题 → 出包 apk-m1-fix5

### 起因

用户装上 `apk-m1-fix4` 后用了一轮，报回三条（带截图）：

1. **首页列表划不动**
2. **没有图片的卡，缩略图那儿应该是占位符，现在是个黑框加点**
3. **列表现在看不出来具体是音频输入的，还是文本输入**

### 三条的真根因（都是读代码确认的，不是猜）

| 问题 | 根因 |
|---|---|
| ① 划不动 | `apps/mobile/src/app/index.tsx` 的记忆流容器是**普通 `<View style={styles.list}>`**，既无 `ScrollView` 也无 `FlatList` —— 这个列表**从来没有滚动能力** |
| ② 黑框加点 | `CardRow.tsx` 的无图占位块 = `surfaceAlt` 底色 + **无边框** + 中间一个 `·`；深色模式下 `surfaceAlt(#212428)` 与卡片 `surface(#191B1E)` 几乎同色 ⇒ 看着像控件坏了 |
| ③ 分不出输入来源 | 卡片只有标题 + 角标，角标一清掉（转写/解析完成）就分不出语音还是打字；`card.source`（`voice`/`text`/`photo`）这个字段本来就有但列表没用 |

### 改法

- `index.tsx`：`View` → `ScrollView`；`padding`/`gap` 从 `style` 挪到 `contentContainerStyle`
  （新增 `styles.listContent`）—— **留在 `style` 上会压掉内容区、滚动时首尾卡片贴边**。
- `CardRow.tsx`：占位块加 `hairline` 描边 + 来源图标；新增 `SOURCE_ICON`/`SOURCE_LABEL`/`sourceOf()`；
  `titleOf` 的空标题兜底改成按来源（「（语音）」「（照片）」「（文字）」）；`subtitleOf` 首段加来源、
  把分类 Emoji 从缩略图接过来（缩略图位现在归来源）。
- 顺带纠术语打架：空标题原来一律「（待整理）」，而「待整理」是 `needs-organize` 角标的专用词。

### 新学到的判据（已写进 `开发交接.md` 铁律与真机 UI 问题清单）

**「划不动」≠「点不动」，别拿层叠遮挡去套：**

| 现象 | 大概率是 |
|---|---|
| 能看见的元素点不到、返回键也无效 | 上面盖了透明的全屏层（`position:absolute` / `<Modal visible>` 简写 / `zIndex`） |
| 手指拖动有回弹、内容纹丝不动 | **没有滚动容器**（外层是 `View` 而非 `ScrollView`/`FlatList`） |

另一条：「没有内容时显示什么」也是设计的一部分 —— 占位符必须**在深色模式下**看一眼，
并且给它一个轮廓 + 一个有意义的内容，光画一个点会被读成「控件坏了」。

## 第十二版：模型能力探测的假阴性 → 出包 apk-m1-fix6

### 起因

用户贴模型配置页截图：`https://api.deepseek.com` + `deepseek-flash` + Key 已填，
探测却报「图片输入：不可用（模型返回为空）」+「音频输入：不可用（HTTP 422
`unknown variant \`input_audio\``）」。用户原话：**这儿应该配置的是正确的，但是提示错误**。

### 两条报错的成因完全不同（读代码 + 官方文档确认，不是猜）

| 报错 | 根因 | 性质 |
|---|---|---|
| 图片「模型返回为空」 | `capabilities.ts` 的探测写死 `maxTokens: 64`；DeepSeek **thinking 默认开启（effort=high）**，思维链与正文**共用** max_tokens ⇒ 64 个 token 连「想」都走不完 ⇒ 正文必然空。旧代码把「正文空」直接判成「不支持」 | **假阴性**（deepseek-flash 其实支持图片） |
| 音频 422 `unknown variant input_audio` | DeepSeek 的 `/chat/completions` 只接受 `text`/`image_url`/`file`，**确实没有音频能力**（这是真结论），但旧代码把服务端 JSON 原文甩给用户，读起来像配置错了 | 真结论 + 烂文案 |

### DeepSeek 事实（2026-09-19 查 api-docs.deepseek.com，别凭记忆猜）

- 模型名只有 `deepseek-flash` 与 `deepseek-v4-pro`；旧的 `deepseek-chat`/`deepseek-reasoner` 已于 2026-07-24 停用
- `deepseek-flash` **支持图片**；`deepseek-v4-pro` 仅文本
- **全系不支持音频**（chat 没有 `input_audio` 内容块）
- **thinking 默认开启**、默认 effort=high；思考模式下 `temperature` 不生效（不报错但被忽略）；推理在 `reasoning_content`
- `max_tokens` 不设时：非思考 8K / 思考 64K；官方建议思考模式 ≥2048
- **`input_audio` 基本只有 OpenAI 自己认** ⇒「OpenAI 兼容」≠ 能走 ASR 模式 1，语音转写默认走 `/audio/transcriptions`

### 改法（core provider 层 + 配置页）

- `capabilities.ts`：结论**四态化** `ok` / `unsupported` / `unknown` / `error`；新增 `unknown`
  =「请求被接受了但模型没给正文」，**绝不判不支持**；`maxTokens` 64 → **2048**；
  新增**纯文本连通性探测并优先跑**，`status === 'error'` 时短路（不再白等两个 60s 超时）；
  `classify()` / `explainUnsupported()` 按 HTTP 状态码 + 服务端 body 翻译成人话
- `types.ts`：新增 `HttpStatusError`（带 `status`/`body`）与 `UnsupportedInputError`（本地判定），
  调用方不必再靠 message 正则猜
- `openai-compat.ts`：读 `reasoning_content`，`ChatResponse.reasoning` 在 text 为空时带出来
- `settings.ts`：`CapabilityCache` 加可选 `text` / `textDetail`（旧缓存兼容）
- `provider.tsx`：`probeSummary()` 三段式（配置连通性 / 图片分析 / 语音识别，连通性放第一行）；
  「上次探测」用 `capsMark()`，旧缓存缺项显示「未记录」而不是「不支持」

### 顺带发现的真伤害

`runtime.tsx` 的 `visionSupported()` 在「已探测且明确不支持」时会**锁死图片分析开关**
⇒ 用户装的 fix5 里，**拍照卡的图片从来没被送进过模型**。重探一次即解除。

### 同一类错误的第二个实例（写这版时一并堵掉，为此取消了一次已跑 12 分钟的构建）

`probeLlm` 原来把 `vision` 直接写成 `vision.ok` ⇒ 「没测出来」（`unknown`）也会让 `vision=false`
⇒ **同样会锁死图片分析**。而 `visionSupported()` 的注释本来就写「只有明确不支持才锁死」，
是那个布尔判定违背了它自己的约定。现在只有 `status === 'unsupported'` 才置 false；
`ProbedCapabilities` + `CapabilityCache` 另加 `visionStatus`/`audioStatus` 给 UI 区分三态。

**教训延伸**：把三态压成一个布尔下发时，**必须想清楚「第三态映射到哪一边」**，
并选**代价小的那一边**（这里 false 的代价是关掉用户功能，true 的代价只是白试一次）。

### 新判据（已进交接文档铁律）

**「请求成功了但没拿到想要的内容」≠「这个功能不可用」。**
判据要落在「HTTP 层是否被接受」，不是「内容是否如期返回」；下结论前先怀疑自己的请求参数
（输出上限 / 超时 / 格式）。

### 踩到的两个坑（都已写进交接文档）

- **同一文件的两个 Edit 并行发会丢写**：`anthropic.ts` 与 `openai-compat.ts` 各有一次改动被覆盖，
  靠 grep 核对才发现（测试红了才暴露）。**同文件的编辑一律串行。**
- **`git push` 静默挂死 10 分钟**：system 级 `credential.helper=helper-selector` 在非交互 shell 里
  拿不到凭据。用 `gh auth setup-git` 修好。**判断法：push 超过 1 分钟没输出就是它在等凭据。**

  探测 maxTokens 下限、错误分类、配置失败短路、**unknown 不锁死图片分析**、unsupported 才锁死）；
  mobile `tsc` 通过；`expo export` 通过

## 第十三版：砍掉「LLM 原生音频」这条从未实现的路 → 出包 apk-m1-fix7

### 起因

用户提问：「现在市场的大模型是不是确实并没有原生的语音读取能力，而是靠其他手段去转文字实现的？
我们的靠模型识别语音这块是不是需要砍掉，只留 ASR？或者说改改需求，我们就不要语音识别，
因为现在的用户手机上基本都有语音转文本的能力。」

### 读代码后的决定性发现

**需求 3.2 标着「推荐默认」的 ASR 模式 1（LLM 原生音频）从来没被实现过。**
`{type:'audio'}` 这个 `Part` 全仓**只在能力探测里被构造过一次**（`capabilities.ts` 的 `samplePart`）；
业务流水线（`capture.ts` / `queue.ts` / `runtime.tsx`）**一次都没把音频送给主 LLM** ——
转写始终只走 `deps.asr.transcribe`（`/audio/transcriptions`）。

而且**那项音频探测不控制任何功能**：`vision` 会经 `visionSupported()` 锁死图片分析开关，
`audio` 只在两处显示（设置首页的 Chip + 探测结果那一行）。⇒ **删它 = 零行为变化。**

### 市场事实（查证过）

| 架构 | 谁在用 | 增量 |
|---|---|---|
| pipeline（先转写再理解） | 绝大多数厂商 | 无 |
| native audio tokens | Gemini（最强）、OpenAI 的 audio 系 | 韵律 / 情绪 / 非语音声音 |

原生音频是真的，但对本产品是错的：**那个增量对检索是噪声**；权威口径明确「转写+LLM 更便宜更快，
原生音频约 25 倍延迟」；音频 token 单独计价（比文字贵一个量级）。
更关键的两条：**拿不到热词**（房间名 / 物品名恰是本产品最需要搜准的实体 ⇒ 准确率更差）；
**各家入参互不相同**（Anthropic 无音频输入、Gemini 走 File API 而非内联 base64）。

### 为什么不改端侧识别（用户提的另一条路）

- Android `SpeechRecognizer` 是**麦克风实时识别**，**不能转写已录制的音频文件** ⇒ 要迁就它就得推翻
  「先落盘、后异步解析」这条红线（素材永不丢失 + 飞行模式先录）
- 「离线可用」在真机上不成立：默认走 Google 服务（要 GMS + 联网），离线要预装语音包、中文方言 /
  专业词很差 —— 而本产品最需要它的场景（地下室 / 储藏间 / 车库）恰恰无网
- 两端行为分叉（iOS 的 SFSpeechRecognizer 支持文件转写）；且没有热词接口
- **收敛**：想用手机自带转文字 → 用**输入法听写**打进文本框，走已完整支持的纯文本录入路径，零开发成本

### 改法（纯减法；`Part` 一收敛，编译器就替我们找漏改点）

- `providers/types.ts`：`Part` 删 audio 变体；删掉已无生产者的 `unsupportedInput`
  （连带 `capabilities.classify` 里那个判定）
- `providers/openai-compat.ts`：删 `input_audio` 分支（`else` 直接走 image）；类注释改成「不发音频」
- `providers/anthropic.ts`：audio 拒绝分支删掉，`else` 走 image
- `providers/capabilities.ts`：`CapabilityKind` 收敛为 `text | vision`；`probeLlm` 由
  「纯文本 + 并发图片/音频」改为「纯文本 → 图片」两次请求；删 audio 三字段与音频的人话翻译
- `settings.ts`：`CapabilityCache` 删 `audio*`（旧缓存冗余键被 JSON 宽松忽略，安全）
- `providers/samples.ts`：1 秒 WAV **保留**（设置页 ASR 槽探测还在用它），只更新注释
- `apps/.../settings/provider.tsx`：`probeSummary` 三段降两段；「上次探测」与 SectionTitle hint 同步
- `apps/.../settings/index.tsx`：删「关于」里的「音频输入」Chip
